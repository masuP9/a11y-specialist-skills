## 抜き出す単位

定義や一般原則を再掲せず、判定が変わる条件を一項目にする。元文書の例を一般化しすぎず、例外・適用範囲・必要な組み合わせを要約と一緒に残す。

| 項目 | 記載内容 |
| --- | --- |
| ID・論点 | `<達成基準>-E<連番>` と判断上の問い。日英で同じIDを使い、削除したIDは別の論点に再利用しない |
| 種別・出典 | 規範 / Understanding / Technique（Sufficient・Advisory、必要な併用）/ Failure / ACT / 技術仕様。文書名、節名、節URL |
| 要約 | 原文が支持する判断条件。引用や独自判断と混同しない |
| 適用条件・限界 | 対象、例外、追加確認、そこから言えないこと |
| 確認情報 | 原文確認日と版。ファイル共通なら冒頭にまとめる。ACTは承認状態とルールの版も記録する |

「線引き」の各項目から根拠IDを参照する。独自の運用判断は `[独自: 理由。根拠: …]` と明示する。著者が意図して採用した方針は [独自] として保持し、理由・適用範囲・報告方法を記す。公式解釈であるとは主張しない。出典について、原文を取得できない、または支持する箇所が見つからない場合は `[未確認: 足りない根拠]` とし、確定判定の根拠にしない。

## 判断を進めるための書き方

- 通常例で採る判断を先に示し、その判断を変える具体的な条件と、確認する材料を続ける。「場合による」「要確認」だけで終わらせない。
- 原文が示す適合・例外の例を、網羅的な必要条件に読み替えない。一方、例を広げて採用する運用は、理由と適用範囲を示して [独自] と区別する。
- 採用済みの既定方針に当てはまる例を、抽象的な不確実性だけで毎回要確認に戻さない。追加確認は、その方針から外れる具体的な兆候や不足情報に結び付ける。

## 出典の扱い

- WCAG本体を規範として参照し、Understanding・Techniques・ACTは補助資料として区別する。
- Techniqueの未使用やテスト失敗だけでWCAG不適合にしない。Failureも対象と条件を照合する。[Understanding Techniques](https://www.w3.org/WAI/WCAG22/Understanding/understanding-techniques)
- ACTの適用範囲、前提、WCAGへの結果の対応を確認する。passを達成基準全体の適合に広げない。Proposed / Deprecatedを承認済みの現行ルールと混ぜない。[About ACT Rules](https://www.w3.org/WAI/standards-guidelines/act/rules/about/)
- 公開されたW3C原文を確認する。編集者草案や日本語訳を補助に使う場合は区別する。日本語を編集上の正本としてから英訳するが、根拠の内容はW3C原文と照合する。
- 随時更新のページはその旨と確認日を記録する。固定版URLがあれば使う。確認日だけでは過去の本文を復元できないため、厳密な再現が必要な更新では元リポジトリのcommit等も記録する。未取得の版やハッシュを書かない。

## 基準ごとの完了確認

1. 原文の該当節を開き、文書のID・達成基準との対応・条件を確認する。既存の線引きを正当化するために根拠を選ばない。
2. 各線引きと根拠を照合する。出典が支持しない内容を公式の判断として断定している場合は修正、削除、または未確認にする。著者の判断として採用する場合は [独自] と理由を明示する。
3. 不適合になる例、例外で不適合にならない例、材料不足で要確認になる例で読み方を確認する。独自例をW3Cの例と表記しない。
4. 自動チェックの対応表・部品索引・参照元に矛盾がないか確認する。ツール固有の挙動は実装を確認し、W3Cの要件と区別する。
5. 英語版のID・出典・条件を同期し、リンクと `npm run validate:skills` を確認する。

試作の形式を確認した後は、関連基準を3〜5件ずつ処理し、最後に基準間の矛盾と未確認箇所を横断確認する。レビュー対象は要約の読みやすさだけでなく、原文がその判断を支持するか。
