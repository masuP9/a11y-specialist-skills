# 2.1.2 No Keyboard Trap

- Scope: Components/regions entered using a keyboard, including modals, embeds, and states opened by interaction
- Materials: Entry, exit operation, resulting focus, and instructions for nonstandard methods
- Automated check: `keyboard-trap-check`. Separate limited exit attempts from the SC verdict
- Sources checked: 2026-11-02. WCAG: Recommendation of 2024-12-12; Understanding / Techniques: living published pages. The following are summaries, not quotations.

## Evidence

### 2.1.2-E01 — Check keyboard exit, not just cycling Tab

- **Type / source:** [Normative — No Keyboard Trap](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#no-keyboard-trap), [Understanding — Intent](https://www.w3.org/WAI/WCAG22/Understanding/no-keyboard-trap.html#intent).
- **Summary:** Confining focus within a modal or similar region is not a failure if users know how to leave using only the keyboard. Check instructions when exit requires more than unmodified arrows, Tab, or standard exit methods.
- **Conditions / limits:** Standard methods depend on the environment. Escape is standard in many physical-keyboard environments, but is not a mandatory exit key. Modal ARIA attributes do not prove an exit exists.

### 2.1.2-E02 — Check instructions and actual operation together

- **Type / source:** [Technique — G21 “Description / Tests”](https://www.w3.org/WAI/WCAG22/Techniques/general/G21#description) (Sufficient), [Failure — F10 “Description / Tests”](https://www.w3.org/WAI/WCAG22/Techniques/failures/F10#description).
- **Summary:** Try the exit keyboard operation or the operation documented in accessible help. Check failure conditions when keyboard entry is possible but exit requires a pointer or closing/restarting the browser.
- **Conditions / limits:** A visible close control is insufficient. Check keyboard reachability, activation, and return outside the region. Keyboard users must be able to access instructions for nonstandard methods.

### 2.1.2-E03 — Apply non-interference even to content with alternatives

- **Type / source:** [Normative — Non-Interference](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#cc5).
- **Summary:** This criterion also applies to content not relied upon for conformance.
- **Conditions / limits:** A separate alternative link does not exempt an embedded component's trap.

## Judgment lines

- Pass when users can leave a keyboard-entered region with the keyboard alone and access any required instructions. Tab cycling internally alone is not Fail. [Evidence: 2.1.2-E01–E02]
- Escape may be absent if a close control works through standard keyboard operation or another instructed key exits. Fail confirmed absence of keyboard exit, or a solely nonstandard exit without required instructions. [Evidence: 2.1.2-E01–E02]
- Successful DOM `click()` on a close control does not prove keyboard operation. Closing the browser or pointer-only exit is not a conformance route. [Evidence: 2.1.2-E02. Inspection mapping is ours]
- Do not call an unreachable component a trap under this criterion; assess functionality under [2.1.1](./2.1.1.md). Even with another alternative, assess traps in content users can enter. [Evidence: 2.1.2-E01, E03]

## Judgment examples

- **Pass:** Tab cycles inside a modal, but activating its close button with the keyboard returns outside. Missing Escape alone does not fail this SC. [Evidence: 2.1.2-E01–E02]
- **Pass:** An editor uses Tab for input, but an exit key documented in accessible instructions moves to subsequent content. [Evidence: 2.1.2-E01–E02]
- **Fail:** Leaving an embed requires clicking outside with a pointer. A link to equivalent functionality does not exempt it. [Evidence: 2.1.2-E02–E03]
- **Needs review:** The tool's three attempts failed, but the component has help for custom keys. Check access to help, instructions, and actual exit. [Our interpretation: inspection example. Evidence: 2.1.2-E01–E02]

## When building

- When confining focus, provide a keyboard-only exit and accessible instructions for nonstandard methods. [Evidence: 2.1.2-E01–E02]

## When checking

- **Implementation checked:** `runKeyboardTrapCheck.ts`, `normalizeKeyboardTrapCheck`, and `rule-registry.ts`. A tail set from Tab navigation produces candidates. On a representative element, it tries Escape, Shift+Tab, and DOM `click()` on a close control found by name. All failing yields `confirmedTraps` / `violations`; successful exit generally yields `needsReview` / `incomplete`. A candidate with `role="dialog"` + `aria-modal="true"` and working Escape is not reported.
- **Confirmed:** Even these implementation `violations` need comparison with untested exit routes/instructions before the SC verdict. Fail defects confirmed to prevent keyboard exit. [Evidence: 2.1.2-E01–E02. Result-comparison reporting policy is ours]
- **Remaining:** `details.tabWalkCapped`, iframe/shadow-root interiors, dynamic inert/element changes, and other user-opened states. Normalization does not reflect `tabWalkCapped` in verdicts, so inspect truncation and untested scope even with passes.
- **Do not overclaim:** Three failed attempts do not prove no exit; a successful click does not prove keyboard conformance; zero candidates do not establish page-wide conformance. [Evidence: 2.1.2-E01–E03]
