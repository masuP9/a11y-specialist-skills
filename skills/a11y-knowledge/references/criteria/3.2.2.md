# 3.2.2 On Input

- Scope: Changes of context caused by changing component settings/values
- Materials: Prior instructions, distinction between value change/activation/focus, before-and-after screen, URL, and focus
- Automated check: `change-on-input-check`. Findings are candidates to compare with prior advice
- Sources checked: 2026-11-02. WCAG: Recommendation of 2024-12-12; Understanding / Techniques: living published pages. The following are summaries, not quotations.

## Evidence

### 3.2.2-E01 — Separate setting changes from activation, content from context

- **Type / source:** [Normative — On Input](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#on-input), [Understanding — Intent / Examples](https://www.w3.org/WAI/WCAG22/Understanding/on-input.html#intent).
- **Summary:** Check whether changing a value/setting automatically changes context. Distinguish ordinary link/submit-button activation, but include buttons whose pressed state or other setting changes.
- **Conditions / limits:** Adding fields or updating options meets this SC if basic context remains. Do not equate URL/DOM changes with context changes. Becoming disabled is included in the explanation of setting changes, but disabling alone is not automatically a context change.

### 3.2.2-E02 — Accept changes explained before use

- **Type / source:** [Technique — G13 “Description / Tests”](https://www.w3.org/WAI/WCAG22/Techniques/general/G13#description) (Sufficient).
- **Summary:** Check that users can learn what changing the setting will do before using the component. Advice can occur earlier in reading order, in a required preceding step, or in mandatory training before use.
- **Conditions / limits:** Do not require adjacent text or a particular ARIA attribute. Post-change notifications or merely having optional help do not prove prior advice. Compare the advice with actual behavior.

### 3.2.2-E03 — Keep updates in context or use explicit activation

- **Type / source:** [Technique — G80 “Description”](https://www.w3.org/WAI/WCAG22/Techniques/general/G80#description) (Sufficient using a more specific technique), [SCR19 “Description / Tests”](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR19#description) (Sufficient), [Failure — F36 “Description”](https://www.w3.org/WAI/WCAG22/Techniques/failures/F36#description), [F37 “Tests”](https://www.w3.org/WAI/WCAG22/Techniques/failures/F37#tests).
- **Summary:** Options include separating value changes from submission or updating subsequent options while preserving context. Check failure conditions for unannounced automatic submission/new windows.
- **Conditions / limits:** Requests, saving, and change events are not themselves prohibited. Apply the normative prior-advice condition to F36 too. Advice satisfying 3.2.2 does not resolve separate [2.1.1](./2.1.1.md) issues, such as navigation on each selection preventing keyboard choice.

## Judgment lines

- Pass when setting/value changes do not change context. Context changes also pass this SC when users were advised beforehand. Fail when both the actual change and missing advice are confirmed. [Evidence: 3.2.2-E01–E03]
- Check new pages/windows, focus moving to another component, etc. caused by value changes. Do not fail mere history updates or result updates retaining context. [Evidence: 3.2.2-E01]
- Distinguish ordinary submit/open buttons as activation and toggles as setting changes. Assess changes caused solely by receiving focus under [3.2.1](./3.2.1.md). Do not transfer 3.2.2's prior-advice allowance to 3.2.1. [Evidence: 3.2.2-E01–E02, 3.2.1-E01]
- Treat advice that does not describe the context change as inadequate: for example, “autosaves” when a different screen opens. Confirmed advice in a preceding step does not fail merely because it is absent beside the field. [Evidence: 3.2.2-E02. Advice-comparison examples are ours]

## Judgment examples

- **Pass:** Choosing a country updates subsequent region options while preserving focus and the form's overall context. [Evidence: 3.2.2-E01, E03]
- **Pass:** A form's opening instructions explain that completing each split telephone-number field moves focus to the next. [Evidence: 3.2.2-E01–E02]
- **Do not flag under this SC:** Activating Submit or standard Enter submission opens results; changing the value alone does not. [Evidence: 3.2.2-E01, E03]
- **Fail:** Completing and leaving the final field submits and opens a new page without advance advice. [Evidence: 3.2.2-E02–E03]
- **Needs review:** The tool detects navigation after selection, but instructions from the preceding step are unavailable. Check prior advice and the actual navigation. [Our interpretation: inspection example. Evidence: 3.2.2-E02]

## When building

- Separate updates from context changes and use explicit submission where appropriate. Explain setting-triggered context changes before operation. [Evidence: 3.2.2-E01–E03]

## When checking

- **Implementation checked:** `runChangeOnInputCheck.ts`, `normalizeChangeOnInputCheck`, and `rule-registry.ts`. It changes main-frame select/radio/checkbox/text-like controls with one value, reporting navigation, new windows, focus movement, and dialogs as `incomplete`. `untested` and `aborted` also require review.
- **Confirmed:** Results after comparing whether the value change caused an actual context change and whether advice preceded it. [Evidence: 3.2.2-E01–E03]
- **Remaining:** Toggle buttons, custom ARIA widgets, iframe/shadow roots, unsupported input types, other values, delayed reactions, and large panel replacements. The tool does not assess prior advice. Restoring values does not restore handlers' internal state.
- **Do not overclaim:** Findings are not immediate Fail; zero candidates are not whole-SC Pass. A control skipped due to an on-focus change is not tested for on-input behavior. [Evidence: 3.2.2-E01–E03]
