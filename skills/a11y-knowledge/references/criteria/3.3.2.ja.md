# 3.3.2 ラベル又は説明

- 対象の部品: データ入力を受けるform、input、checkbox、radio、switch、combobox、listbox、slider
- 要る材料: 見えるラベル・説明、入力中の表示、受け付ける形式、名前の出どころ
- 自動チェック: axeの `label` は名前の実装の材料。3.3.2の適否は確定しない
- 原文確認日: 2026-11-02。WCAGは2024-12-12勧告、Understanding / Techniquesは随時更新のWCAG 2.2公開ページ。以下は引用ではなく要約。

## 根拠

### 3.3.2-E01 — 名前の計算結果と利用者への提示を分ける

- **種別・出典:** [規範 — Labels or Instructions](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#labels-or-instructions)、[Understanding — Intent](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html#intent)。
- **要約:** 任意入力も対象。全利用者へのラベル又は説明の提示を評価し、プログラム的関連付け（1.3.1）やアクセシブル名（4.1.2）と区別する。データ入力に関係しないリンク・開閉操作は対象外。
- **適用条件・限界:** 名前がないだけで本基準のFailにしない。逆に `aria-label` や視覚的に隠したラベルだけでは、見える説明を代替できない。

### 3.3.2-E02 — 画像や文脈を含め、実際のラベルを確認する

- **種別・出典:** [Understanding — Examples](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html#examples)、[Technique — G131「Description」](https://www.w3.org/WAI/WCAG22/Techniques/general/G131#description)（3.3.2では、より具体的なTechniqueを用いるSufficient）。
- **要約:** 検索欄の虫眼鏡等、対象利用者に理解される画像ラベルも使える。欄ごとの意味を確認し、すべてに独立した可視テキストを機械的に要求しない。
- **適用条件・限界:** 分割入力ではグループの説明と各欄の識別を併せて確認する。ラベルの明確さ・説明性は2.4.6でも別に評価する。

### 3.3.2-E03 — 必須・形式の手掛かりを必要に応じて示す

- **種別・出典:** [Technique — H90「Description」](https://www.w3.org/WAI/WCAG22/Techniques/html/H90#description)（G131との併用でSufficient）、[Understanding — Intent](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html#intent)。
- **要約:** 必須を示す文字・記号をラベルやlegendに含め、記号なら初出前に意味を説明できる。独自の入力形式など必要な説明を用意する。長い説明をフォーカス時に提示する方法もある。
- **適用条件・限界:** すべての欄に形式例を要求しない。実際に受け付ける値と説明を照合する。

### 3.3.2-E04 — F82を形式説明不足一般に拡張しない

- **種別・出典:** [Failure — F82「Description」「Tests」](https://www.w3.org/WAI/WCAG22/Techniques/failures/F82#tests)。
- **要約:** 電話番号の分割欄を括弧やハイフンだけで示し、可視のラベルも入力説明もないケースを扱う。
- **適用条件・限界:** F82の両方のテストがfalseとなる条件を照合する。一般の日付形式やハイフン指定の説明不足の出典としては使わない。

## 線引き

- 可視のラベル・説明があるが名前の関連付けがない場合、3.3.2の提示条件は満たし得る。1.3.1 / 4.1.2は別途評価する。[根拠: 3.3.2-E01]
- placeholderしかなく入力中にラベル・説明が失われる欄は、本知識ベースでは3.3.2不適合とする。ほかの可視ラベル・説明がある場合や、入力後もラベルとして残る実装にはこの判定を適用しない。[独自: 入力中も目的を確認できることを重視する著者方針。参考根拠: 3.3.2-E01–E02]
- placeholder由来の名前という理由だけで1.3.1 / 4.1.2不適合にしない。関係や名前の別の欠陥まで免除しない。[独自: 基準間の分担。参考根拠: 3.3.2-E01]
- axe-core 4.14.0の `label` は `wcag412` に対応し、非空のplaceholderも通過経路に含む。violationを3.3.2のFailへ直接転記せず、passも3.3.2適合にはしない。[独自: ツールとの対応。実装確認: `node_modules/axe-core/axe.js` の `label` ルール。参考根拠: 3.3.2-E01]

## 判断例

- **適合:** 検索欄の目的が虫眼鏡の画像ラベルで伝わり、自由入力を受け付ける。独立した可視テキストや入力形式例がないだけでは指摘しない。[根拠: 3.3.2-E02–E03]
- **不適合:** 独自の会員番号形式しか受け付けないのに必要な入力説明がない。電話番号の分割欄に括弧・ハイフンだけがありラベルも説明もない場合はF82の条件に当たる。[根拠: 3.3.2-E03–E04]
- **適合例:** Understandingの電話番号3分割の例は、可視のグループ名「電話番号」と、各欄を識別するtitleを組み合わせる。グループ名も説明もないF82の例とは区別し、各欄に独立した可視ラベルがないことだけでは指摘しない。[根拠: 3.3.2-E02–E04]
- **要確認:** a11y treeに名前があるが、可視のラベルの有無が分からない。画面と入力後の表示を取得する。[独自: 検査方針。根拠: 3.3.2-E01]

## 作るとき

- 通常の入力欄には見えるlabelを使い、placeholderは補助ヒントにする。視覚的に隠したlabelへの変更だけで可視の説明不足を解決したことにしない。[独自: 著者の実装方針。参考根拠: 3.3.2-E01–E02]
- 必須の表示と必要な形式の説明を用意し、記号の意味を初出前に伝える。[根拠: 3.3.2-E03]

## 確かめるとき

- **確定:** 表示・入力条件を手動で照合した結果。axeの名前チェックだけでは確定しない。[3.3.2-E01–E04]
- **残る:** 任意項目、選択肢、グループ、入力中のラベル、必要な形式・必須の説明。
- **言い切らない:** 名前の有無を可視ラベルの有無に読み替えない。[根拠: 3.3.2-E01]
