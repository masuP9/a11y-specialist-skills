# 3.3.8 アクセシブルな認証（最低限）

- 対象: 既存の利用者の認証の各ステップ（多要素認証、アカウント復旧、条件付きで出るCAPTCHAを含む）
- 要る材料: 認証の全経路とステップ、各ステップで求める操作、貼り付け・自動入力の実測、CAPTCHAの実際の出題内容
- 自動チェック: `accessible-authentication-check`は候補を出す。別の手段の有無と出題内容は判定しない
- 原文確認日: 2026-11-05。WCAGは2024-12-12勧告。公開ページ（随時更新）の更新日はUnderstanding 2026-09-06、G218 2025-07-15、H100 2026-01-12、F109 2026-04-27。以下は引用ではなく要約。

## 根拠

### 3.3.8-E01 — 認知機能テストに当たるものを分ける

- **種別・出典:** [規範 — Accessible Authentication (Minimum)](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#accessible-authentication-minimum)、[用語 — cognitive function test](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#dfn-cognitive-function-test)、[Understanding — Cognitive Function Tests](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html#cog-fun-tests)。
- **要約:** 記憶、文字の転記、正しいつづり、計算、パズルが該当する。サイト固有のパスワードの記憶やパターンのジェスチャーも含む。
- **適用条件・限界:** 氏名・メールアドレス・電話番号は本人に固有でサイト間で変わらない識別子として、記憶のテストに含めない。サイト固有のユーザー名はこの扱いにしない。

### 3.3.8-E02 — 対象の手順を決める

- **種別・出典:** [Understanding — Intent](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html#intent)、[Cognitive Function Tests](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html#cog-fun-tests)、[Object Recognition](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html#object-recognition)。
- **要約:** 既存の利用者の認証が対象。多要素認証は全ステップが条件を満たす経路が必要。アカウント復旧で本人確認をするなら、認知機能テストではない方法が要る。広告ブロッカーの検出や繰り返しの誤入力で出るテストも対象。
- **適用条件・限界:** ユーザー名の作成やアカウントの開始は対象外。貼り付けを妨げないことなどは新規登録でも負担を減らすが、この基準の要件にはしない。

### 3.3.8-E03 — 認知機能テストを使わない別の手段を確認する

- **種別・出典:** [規範 — Accessible Authentication (Minimum)](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#accessible-authentication-minimum)、[Understanding — Examples](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html#examples)、[Two-factor authentication systems](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html#two-factor-authentication)、[G218「Tests」](https://www.w3.org/WAI/WCAG22/Techniques/general/G218#tests)（Sufficient）。
- **要約:** メールのリンク、WebAuthn、OAuthによる第三者ログイン、ハードウェアキー、OSの認証、QRコードの読み取り、端末への通知による確認を例に挙げる。
- **適用条件・限界:** 転記が要る音声CAPTCHAは別の手段にならない（[Cognitive Function Tests](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html#cog-fun-tests)）。WebAuthn・OAuthは手法としては将来の候補だが、Understandingの例に挙がる。G218の物の認識に関する手順5はAAAだけの条件。

### 3.3.8-E04 — 貼り付けと自動入力を止めていないか確認する

- **種別・出典:** [規範 — 注記2](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#accessible-authentication-minimum)、[Understanding — Login forms](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html#login-forms)、[Copy and paste](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html#copy-paste)、[H100「Description / Tests」](https://www.w3.org/WAI/WCAG22/Techniques/html/H100#description)（Sufficient）。
- **要約:** 規範の注記2は、パスワード管理ソフトへの対応と貼り付けを支援の例に挙げる。Understandingは、自動入力の妨害と貼り付けの妨害のどちらも、別の手段がなければFailとする。H100の手順は、適切な名前と貼り付けの許可を確認する。
- **適用条件・限界:** H100はメールとパスワードだけのログインの手法。例に`autocomplete`があるが、手順の確認項目ではない。1.3.5と4.1.2を満たす欄は通常認識されるという記述は、実際の入力の保証ではない。

### 3.3.8-E05 — 分割入力や別の形式での入力を確認する

- **種別・出典:** [Failure — F109「Description / Tests」](https://www.w3.org/WAI/WCAG22/Techniques/failures/F109#description)、[Understanding — Copy and paste](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html#copy-paste)。
- **要約:** 作成時と異なる形式での入力を求めるとFailに当たる。各桁の分割欄で全体を一度に貼り付けられないもの、「2文字目と6文字目と最後」の入力、1文字ずつの`select`が例。
- **適用条件・限界:** 最初の欄に全体を貼り付けて残りの欄にも入るなら、F109の例に当たらない。全文字でも一部の文字でも適用する。別の手段があればF109は成立しない。

### 3.3.8-E06 — 確認コードは貼り付けで判定する

- **種別・出典:** [Understanding — Two-factor authentication systems](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html#two-factor-authentication)。
- **要約:** 手入力での転記を必須にする確認コードは適合しない。少なくとも貼り付けができ、ユーザーエージェントの自動入力を許す必要がある。
- **適用条件・限界:** コードが別の端末に届く場合、クリップボードへ渡せるとみなして評価する。評価するのはコンテンツが貼り付けを受け付けるかで、端末間の受け渡しの可否は範囲外。

### 3.3.8-E07 — 物の認識と本人提供の内容の範囲を確認する

- **種別・出典:** [規範 — Accessible Authentication (Minimum)](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#accessible-authentication-minimum)、[Understanding — Object Recognition](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html#object-recognition)、[Personal Content](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html#personal-content)。
- **要約:** 触れて見られる物（乗り物・動物を含む）の認識と、利用者が提供した非テキストの識別は例外。画像・映像・音声のいずれでもよい。
- **適用条件・限界:** サイトが決めた語の記憶・転記、サイトが提供した画像の認識、認識を超える課題（猫と犬の数を掛ける等）、テキストの本人情報は例外にしない。文化による物の違いは、アクセシビリティ特有の問題とは扱われない。AAAの3.3.9にはこの例外がない。

### 3.3.8-E08 — その他のテストと文字の非表示を分ける

- **種別・出典:** [Understanding — Other types of cognitive tests](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html#other-cognitive-tests)、[Hiding characters](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html#hiding-content)。
- **要約:** 計算や視覚的なパズルは例外にならず、別の手段が要る。パスワードの表示切替は、負担を減らす任意の機能として挙げられる。
- **適用条件・限界:** 表示切替をこの基準の必須条件にしない。パスワード管理ソフトへ保存するパスワードの作成など、手入力が要る場面があることも原文は認めている。

## 線引き

- 認証の各ステップで、認知機能テストがないか、別の手段・支援・物の認識・本人提供の内容のいずれかが成立すればPass。どれも成立しなければFail。[根拠: 3.3.8-E01–E04, E07]
- パスワードやコードの欄が貼り付けを妨げ、別の手段がなければFail。自動入力が動くことだけでは、この判定を変えない。[独自: 規範の注記2は例の列挙で、Understandingの「自動入力の妨害又は貼り付けの妨害」をFailとする読み方を採用する。既存の判定方針を維持。根拠: 3.3.8-E04]
- 別の手段は、その経路の全ステップが認知機能テストを使わないことを確認して認める。Understandingの例に当たるパスキー・OAuth等が実際に使えるなら、抽象的な不確実性だけで要確認に戻さない。[根拠: 3.3.8-E02–E03]
- `autocomplete="off"`だけではFailにしない。自動入力を実際に試し、スクリプト等で止められていれば、貼り付けが使えても別の手段がなければFail。入れられれば指摘しない。[独自: 属性だけでは「積極的な妨害」を確定できないため。根拠: 3.3.8-E04]
- `autocomplete`の属性がないこと、パスワードの表示切替がないことだけではFailにしない。1.3.5・4.1.2の対象は各基準で判定する。[根拠: 3.3.8-E04, E08]
- CAPTCHAは部品の存在でなく、実際に求められる操作で判定する。出題されないものはテストとして扱わない。認証の外（お問い合わせフォーム、新規登録）のCAPTCHAはこの基準の対象にしない。[独自: 判定の順序。根拠: 3.3.8-E02, E07]
- 物の認識や本人提供の画像で満たす場合はAAのPassとする。3.3.9を評価するときは別に報告し、AAの不適合に混ぜない。[根拠: 3.3.8-E07]

## 判断例

- **Pass:** メールアドレスとパスワードのログインで、貼り付けと自動入力を止めていない。[根拠: 3.3.8-E04]
- **Pass:** パスワードの貼り付けを禁止しているが、メールのリンクやパスキーでも全ステップを完了できる。[根拠: 3.3.8-E03]
- **Pass:** SMSの確認コードの欄へコード全体を貼り付けられる。端末間の受け渡しは評価しない。[根拠: 3.3.8-E06]
- **Pass:** 1桁ずつの欄だが、最初の欄に全体を貼り付けると残りの欄にも入る。[根拠: 3.3.8-E05]
- **Pass:** ログインのCAPTCHAが、車の写真を選ぶだけの課題である。[根拠: 3.3.8-E07]
- **対象外:** 新規登録で新しいパスワードを入力する。[根拠: 3.3.8-E02]
- **Fail:** パスワード欄が貼り付けを拒否し、手入力を促す。別の手段はない。[根拠: 3.3.8-E04]
- **Fail:** パスワードの1・3・5文字目だけを別々の欄へ入れさせる。別の手段はない。[根拠: 3.3.8-E05]
- **Fail:** 誤入力を繰り返すと、歪んだ文字の転記や計算のCAPTCHAが出る。音声版も転記を求め、別の手段はない。[根拠: 3.3.8-E01–E03, E08]
- **Fail:** パスワードの復旧で秘密の質問への文字での回答だけを求める。[根拠: 3.3.8-E02, E07]
- **要確認:** ログインボタンを押してから出るフォームやiframe内の欄で、貼り付けを実測できていない。そのフォームを開いて測る。[独自: 検査例。根拠: 3.3.8-E04]
- **要確認:** 画面にCAPTCHAの部品があるが、繰り返しの誤入力後の出題を確かめていない。出る条件を再現し、課題の種類を記録する。[独自: 検査例。根拠: 3.3.8-E02, E07]

## 作るとき

- 欄に適切な名前と自動入力の値を付け、貼り付けと自動入力を止めない。確認コードは全体を一度に入れられるようにする。[根拠: 3.3.8-E04–E06]
- パスキー・メールのリンク・第三者ログイン等の別の手段を提供すると、利用者が選べる。物の認識や本人提供の内容は例外でも障壁になるため、できれば避ける。[根拠: 3.3.8-E03, E07]

## 確かめるとき

- **実装確認:** axe-core 4.14.0にwcag338タグのルールはない。`accessible-authentication-check`の`auth-paste-blocked`、`auth-autocomplete`、`auth-captcha`はすべて`incomplete`で、別の手段の有無と出題内容を判定しない。
- **確定:** 全経路の各ステップの操作、実際の貼り付け・自動入力、別の手段、出題内容を照合した結果。貼り付けの妨害は`valueAfterPaste`と`pasteEventPrevented`も記録する。
- **候補の扱い:** 貼り付けは2文字の短い文字列で測り、1文字だけ入っても`inserted`になる。分割欄・全体の貼り付けの判定は、実際のコード長で確かめる。`inserted`だけで適合にしない。[根拠: 3.3.8-E05]
- **残る:** 見つからない場所（iframe・shadow root、ボタン操作後のフォーム、`captcha`を名前に含まない独自のもの、後の認証ステップ・復旧の経路）、未計測（`unavailable`、`focus-moved`、見えない欄）。候補0件や対象の欄がないことをPassにしない。未確認の経路を明記して要確認にする。
