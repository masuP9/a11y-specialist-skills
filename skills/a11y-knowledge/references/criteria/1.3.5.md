# 1.3.5 Identify Input Purpose

- Scope: fields collecting information about the user, including select and textarea, not only input
- Inputs needed: measured attributes, labels/instructions, whose information and what purpose the field serves
- Automated checks: autocomplete-audit and axe `autocomplete-valid`; distinguish syntax checks and inferred purposes from final judgments
- Sources checked: 2026-11-02. WCAG is the 2024-12-12 Recommendation; Understanding / Techniques and HTML are living public pages. The following are summaries, not quotations.

## Rationale

### 1.3.5-E01 — Establish scope from the user, listed purpose, and technology support

- **Type / source:** [Normative — Identify Input Purpose](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#identify-input-purpose), [Input Purposes](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#input-purposes), [Understanding — Intent](https://www.w3.org/WAI/WCAG22/Understanding/identify-input-purpose.html#intent).
- **Summary:** Evaluate fields about the user with a listed purpose where the technology supports purpose identification. Search terms and fields clearly collecting another person's information are out of scope.
- **Conditions / limits:** “Shipping address” does not establish another person; the user's own delivery address is in scope. Not every HTML autocomplete token is a WCAG listed purpose.

### 1.3.5-E02 — Check both valid syntax and correspondence to the actual purpose

- **Type / source:** [Technique — H98, Tests](https://www.w3.org/WAI/WCAG22/Techniques/html/H98#tests) (Sufficient), [Technical specification — HTML, Autofill detail tokens](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#autofill-detail-tokens).
- **Summary:** H98 checks both attribute validity and whether the token matches the purpose expressed by the label. Shipping/billing tokens distinguish uses, not people.
- **Conditions / limits:** Neither `on` nor `off` specifies a concrete purpose. Names/IDs or heuristic browser autofill alone are insufficient. H98 is not the only method; alternative metadata needs evidence that assistive technology can use its purpose.

### 1.3.5-E03 — Separate autofill behavior from the combined-purpose exception

- **Type / source:** [Understanding — Intent, autofill and multiple input purposes](https://www.w3.org/WAI/WCAG22/Understanding/identify-input-purpose.html#intent).
- **Summary:** Actual autofill behavior does not determine conformance. When one field accepts username or email and the technology cannot designate both purposes, either purpose or no designation is allowed.
- **Conditions / limits:** Do not extend omission to single-purpose or separate fields. A type such as `email` alone does not adequately identify the specific user information.

## Judgment lines

- An in-scope field with a valid designation matching its actual purpose conforms. An unrelated valid token, `on`, or missing/`off` without another identification method fails. Check the combined-purpose exception first. [Evidence: 1.3.5-E01–E03]
- `autocomplete-audit` derives `expectedToken` from patterns in name / id / accessible name / placeholder; this does not prove the information is about the user. Check applicability before using even an invalid-value violation for an SC verdict. [Our interpretation: policy for matching tool results to scope. Evidence: 1.3.5-E01–E02]
- The current implementation does not flag `on` or an unrelated valid token and does not verify actual purpose correspondence. Zero findings or passes do not establish full 1.3.5 conformance. Missing and invalid values with no inferred purpose remain incomplete evidence. [Our interpretation: tool mapping. Implementation checked: `packages/a11y-audit/src/playwright/runAutocompleteAudit.ts`, `src/utils/axe-format.ts`]
- Missing attribute evidence or uncertainty about whose information is collected requires review with the missing information specified. Separately inspect iframes, Shadow DOM, and custom controls outside the tool's enumeration. [Our interpretation: inspection scope policy. Evidence: 1.3.5-E01]

## Judgment examples

- **Conformant:** The user's email field has `autocomplete="email"`. Do not flag because the user disabled browser autofill. [Evidence: 1.3.5-E02–E03]
- **Non-conformant:** The user's email field has only `autocomplete="given-name"` or `on`, with no other identification method. Valid syntax does not express its purpose. [Evidence: 1.3.5-E01–E02]
- **Not applicable:** A field explicitly asks for another person's gift-delivery address. Do not apply this exclusion to the user's own delivery address. [Evidence: 1.3.5-E01]
- **Do not flag under the exception:** One field accepts username or email and omits purpose identification because both cannot be designated. [Evidence: 1.3.5-E03]
- **Needs review:** The tool inferred `email`, but instructions were not collected and the person concerned is unknown. Obtain the form's use and instructions. [Our interpretation: application example. Evidence: 1.3.5-E01]

## When building

- Use tokens matching the user's information, with shipping/billing and multiple sections as needed. [Evidence: 1.3.5-E01–E02]
- Do not remove purpose identification simply to prevent autofill. Design purpose identification and autofill behavior separately. [Evidence: 1.3.5-E03]

## When checking

- **Settled:** Correspondence between designated and actual purposes after confirming applicability and exceptions. [1.3.5-E01–E03]
- **Remains:** Whose information, semantic correspondence, combined purposes, and fields the tool does not enumerate.
- **Do not assert:** SC conformance from valid strings, successful inference, zero findings, or autofill behavior alone. [Evidence: 1.3.5-E01–E03]
