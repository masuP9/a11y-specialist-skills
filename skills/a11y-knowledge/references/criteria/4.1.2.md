# 4.1.2 Name, Role, Value

- Components: native and custom controls. This knowledge base excludes dialog / alertdialog itself from 4.1.2; buttons, inputs, and other controls inside remain in scope
- Evidence needed: DOM, computed name, role, state and value, accessibility trees before and after operation, and assistive-technology checks where needed
- Automated checks: axe `button-name`, `link-name`, `input-button-name`, and `aria-*` rules
- Sources checked: 2026-11-01. WCAG: Recommendation of 2024-12-12; Understanding / Techniques: WCAG 2.2 published pages (updated in place). The following are summaries, not quotations.

## Rationale

### 4.1.2-E01 — Native elements do not always conform

- **Type / source:** [Understanding — “Intent”](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html#intent).
- **Summary:** Native controls meet the requirement when used according to specification. Changing their role or function through scripts or other means requires additional work.
- **Conditions / limits:** A tag such as `button` plus a name is not enough. Check the actual role, state, value, and notification of changes.

### 4.1.2-E02 — Check the computed name, not attribute presence

- **Type / source:** [Technique — ARIA14 “Description”, “Tests”](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA14#tests) (Sufficient).
- **Summary:** When using `aria-label`, check that the role supports naming and the value describes the control's purpose.
- **Conditions / limits:** This is one technique for cases such as an unavailable visible label. Attribute presence or a non-empty string alone is insufficient. Check visible-label requirements separately.

### 4.1.2-E03 — Check whether state attributes are needed and updated

- **Type / source:** [Technique — ARIA5 “About this Technique”, “Tests”](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA5#tests) (Sufficient in combination with G10).
- **Summary:** Check required states and properties, absence of disallowed ones, and updates reflecting the current state after operation.
- **Conditions / limits:** Do not require `aria-expanded` or similar attributes on every control. Static DOM does not demonstrate updates. ARIA5 alone is not sufficient evidence for the whole criterion.

### 4.1.2-E04 — A naming pass is partial evidence

- **Type / source:** ACT (Approved) [97a4e1 “Applicability”, “Expectation”, “Accessibility Requirements Mapping”](https://www.w3.org/WAI/standards-guidelines/act/rules/97a4e1/#applicability) (version: 2023-08-31).
- **Summary:** The rule checks non-empty names on buttons in the accessibility tree. Even when all pass, 4.1.2 requires further testing.
- **Conditions / limits:** `input type="image"` is excluded. Name presence does not demonstrate state updates or conformance of other controls. Similar axe checks need not be identical implementations.

### 4.1.2-E05 — Separate dialog naming requirements from WCAG verdicts

- **Type / source:** [Technical specification — WAI-ARIA 1.2 “dialog”](https://www.w3.org/TR/2023/REC-wai-aria-1.2-20230606/#dialog) (Recommendation of 2023-06-06), [Tool classification — axe-core 4.14 “aria-dialog-name”](https://dequeuniversity.com/rules/axe/4.14/aria-dialog-name) (checked 2026-11-01).
- **Summary:** WAI-ARIA requires dialog names. axe classifies missing names on dialog / alertdialog as best practice rather than a WCAG rule.
- **Conditions / limits:** The ARIA naming requirement alone does not settle WCAG mapping, and axe classification is not normative WCAG. The exclusion below is an operational judgment adopted by this knowledge base's author, not an explicit W3C exemption.

## Judgment lines

- An in-scope control without a name fails. Having a name alone does not establish conformance for role, state, value, or notification of changes. [Evidence: 4.1.2-E01, 4.1.2-E04]
- When title or placeholder text is actually exposed as the name in the target environment, do not fail solely because of that source. Check visible labels and related requirements separately. [Our interpretation: separating name and label checks. Evidence: 4.1.2-E01, 4.1.2-E02]
- Check actual functionality even on native elements. For example, do not assume the tag conveys the state of a button with added toggle behavior. [Evidence: 4.1.2-E01, 4.1.2-E03]
- Do not require duplicate ARIA attributes when the needed state is exposed natively. For `summary`, check exposure and updates of the expanded state rather than failing solely for an absent attribute. [Our interpretation: native implementation checks. Evidence: 4.1.2-E01, 4.1.2-E03]
- Treat dialog / alertdialog itself as a container for controls and exclude it from 4.1.2. Report missing names as “best practice” improvement candidates without assigning a success criterion. Do not mark 4.1.2 Fail or NT solely for this omission. Evaluate the controls inside normally. [Our interpretation: author’s audit policy. Supporting evidence: 4.1.2-E05]
- Syntax such as `href="#"` alone does not establish a role mismatch. Compare actual behavior with the exposed role. [Evidence: 4.1.2-E01]

## When building

- Use native controls according to specification and check exposed states when adding custom behavior. [4.1.2-E01, 4.1.2-E03]
- Give icon buttons names describing their purpose. Name dialogs, for example by referencing their headings. [4.1.2-E02, 4.1.2-E05]
- Implement the states and values required by custom controls and update them after operation. [4.1.2-E03]

## When checking

- **Improvement candidates:** Mark unnamed dialog / alertdialog as “best practice” and suggest a fix such as referencing the heading with `aria-labelledby`. In audits, report this separately from conformance verdicts. Example: “Best practice (our policy): The dialog has no name. Associate its heading as its name. WCAG success criterion: none assigned.” [Our interpretation: author’s audit policy. Supporting evidence: 4.1.2-E05]

- **Settled:** Fail when missing or mismatched names, roles, required states, or similar information are confirmed for the control. [4.1.2-E01–E03]
- **Remaining:** After naming passes, check roles, states, values, and notification of changes. A browser tree alone does not establish assistive-technology support. [4.1.2-E01, 4.1.2-E04]
- **Do not assert:** Static attributes do not establish conformance of dynamic controls. Do not universally require unnecessary ARIA attributes. Do not reassign a missing dialog name to 1.3.1 or 2.4.6 without separate evidence. [4.1.2-E03–E05]
