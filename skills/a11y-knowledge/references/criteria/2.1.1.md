# 2.1.1 Keyboard

- Components in scope: everything operable (button, link, input, checkbox, radio, switch, combobox, slider, tab, menuitem, option, treeitem, gridcell, listbox, tablist, menu, tree, grid, modal)
- Inputs needed: accessibility tree (tagName, role, focusable, tabindex, disabled), measurement (keyboard-reachability-check from `@a11y-skills/audit`)
- Automated checks: keyboard-reachability-check, axe `scrollable-region-focusable`, and so on

## Rationale

- [Understanding 2.1.1](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html) ([Japanese translation](https://waic.jp/translations/WCAG22/Understanding/keyboard.html))
  - All functionality must be operable with a keyboard. It must not depend on specific timings of keystrokes.
  - The only exception is path-dependent input (handwriting).
  - "Reachable by keyboard" and "operable by keyboard" are different things. There are designs where an element is not reachable by Tab but is operable with arrow keys (roving tabindex, `aria-activedescendant`).
- [G202: keyboard operation for all functionality](https://www.w3.org/WAI/WCAG22/Techniques/general/G202), [F54: pointer-only events](https://www.w3.org/WAI/WCAG22/Techniques/failures/F54), [F55: removing focus as soon as it is received](https://www.w3.org/WAI/WCAG22/Techniques/failures/F55), [APG keyboard interface design patterns](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/)

## Judgment lines

- From the information of a static screen (tree, HTML), it cannot be asserted that something is unreachable or inoperable by keyboard. Do not mark non-conformant solely on the basis of `focusable` or `tabindex`. [Understanding] (roving tabindex, activedescendant)
- A standard HTML element (button / a[href] / input / select / textarea / summary) whose role is still the element's default, that is focusable, and whose tabindex is absent or 0 or more gets the browser's standard keyboard operation, so it is conformant. [Understanding]
- An element with a negative tabindex is not reachable by Tab but may be operable with arrow keys. Needs review (confirm with actual key operation). [Understanding]
- Custom components made of a div or span with a role, and standard elements whose role was changed (tab / menuitem / option / treeitem / gridcell), may be focusable but whether they operate with Enter, Space, or arrow keys cannot be known from the information. Needs review. [Our interpretation]
- When a composite container (listbox / tablist / menu / tree / grid) is confirmed not to receive focus, check keyboard operation on its items without adding a duplicate unresolved judgment for the container alone. Keep the container in scope when it receives focus itself (for example, with aria-activedescendant), or when its focusability is unknown. Retain records of actual key operation as evidence for judgments about the container. [Our interpretation]
- For dialogs, do not mark non-conformant because the container itself is not focusable; check operation of the items inside. [Understanding] (APG)
- Do not ask 2.1.1 of disabled elements where the browser blocks operation (an element on which disabled takes effect, with a disabled attribute, that the browser also judged not focusable). Nobody can operate it, so it is not a keyboard-only problem. Do not exclude `aria-disabled="true"` (the browser does not block operation, and a non-conformance where it can be pressed only with a mouse may be hidden). disabled on an a or div has no effect, so do not exclude those. [Our interpretation]
- An element that measurement (keyboard-reachability-check) reached is only "reachable". Whether it is operable is another matter. An unreached element is needs review because another path (arrow keys) may exist. [Our interpretation]

## When building

- Build interactive components with standard elements (button, a[href], input, select). Do not attach click to a div.
- Custom components (tab, menu, listbox, tree, grid) follow the APG keyboard interaction patterns. Tab enters the container, arrow keys move inside, Enter / Space activates.
- Use only 0 or -1 for `tabindex`. Do not create an order with positive numbers.
- For operations that only work with a mouse (menus that appear on hover, dragging), provide a path to do the same thing by keyboard.
- For components with `aria-disabled="true"`, not only make them look unpressable but also make nothing happen when pressed.

## When checking

- **Settled**: violations of keyboard-trap-check (2.1.2). An element reached by keyboard-reachability-check is settled as "reachable" (whether it is operable is another matter).
- **Remains**: whether custom components operate with Enter, Space, or arrow keys. Whether unreached elements have another path. Confirm by actually pressing keys.
- **Do not assert**: do not mark non-conformant by tabindex or focusable alone. Do not mark disabled elements non-conformant. Do not mark a non-standard component conformant from the information alone.
