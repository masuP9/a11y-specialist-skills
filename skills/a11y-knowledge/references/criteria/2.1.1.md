# 2.1.1 Keyboard

- Scope: interactive components and their functions, including composite widgets and dialog contents
- Inputs needed: elements, roles/states, keyboard reachability and operation, equivalent functional paths
- Automated checks: keyboard-reachability-check, axe `scrollable-region-focusable`, and others; distinguish reachability from execution
- Sources checked: 2026-11-02. WCAG is the 2024-12-12 Recommendation; Understanding / Techniques / APG are living public pages. The following are summaries, not quotations.

## Rationale

### 2.1.1-E01 — Inspect functionality and the nature of input, not individual controls

- **Type / source:** [Normative — Keyboard](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#keyboard), [Understanding — Intent / Examples](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html#intent).
- **Summary:** Every visible control need not be Tab-reachable when the same or comparable function is keyboard operable. Do not require specific individual-keystroke timing such as rapid repetition or prolonged holds.
- **Conditions / limits:** Apply the path-dependent exception to the underlying function, not the input technique. Distinguish freehand drawing from handwriting used for text entry. Dragging to reorder/move does not necessarily depend on the path and needs a keyboard alternative.

### 2.1.1-E02 — Check access and execution for each function

- **Type / source:** [Technique — G202, Tests](https://www.w3.org/WAI/WCAG22/Techniques/general/G202#tests) (Sufficient), [H91, Description / Tests](https://www.w3.org/WAI/WCAG22/Techniques/html/H91#tests) (Sufficient for providing keyboard operation).
- **Summary:** Enumerate functions and verify keyboard-only paths. Standard HTML controls and links can use UA keyboard support.
- **Conditions / limits:** Scripts can obstruct native operation. Another control or shortcut providing the same function can be an alternative; reaching focus alone does not prove execution.

### 2.1.1-E03 — Verify consequences of pointer-only handlers and focus removal

- **Type / source:** [Failure — F54, Tests](https://www.w3.org/WAI/WCAG22/Techniques/failures/F54.html#tests), [F55, Tests](https://www.w3.org/WAI/WCAG22/Techniques/failures/F55.html#tests).
- **Summary:** Check whether pointer-only handlers or immediate blur prevent keyboard use of the function.
- **Conditions / limits:** Do not fail solely for an event name such as click. Check native keyboard activation and equivalent functional paths. Evaluate keyboard traps separately under 2.1.2.

### 2.1.1-E04 — Separate APG recommendations from WCAG requirements

- **Type / source:** [Supporting guidance — APG, Keyboard Navigation Inside Components](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/#kbd_general_within), [Understanding — Intent, keyboard conventions](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html#intent).
- **Summary:** Roving tabindex and aria-activedescendant support navigation within widgets. APG conventions guide implementation/testing; they are not WCAG's only permitted key assignments.
- **Conditions / limits:** An Enter-operable custom button does not fail 2.1.1 solely for lacking Space support. Separately report discoverability improvements for custom keys.

## Judgment lines

- Do not fail from focusable/tabindex alone. Consider arrow-key access or equivalent functional paths for negative tabindex. Fail when functionality is actually unavailable by keyboard and no exception applies. [Evidence: 2.1.1-E01–E04]
- Retain the existing conformant default for native button / a[href] / input / select / textarea / summary with their default roles, focusability, and absent/nonnegative tabindex, relying on native operation. Check execution when there are concrete signs of key cancellation, pointer-only handling, focus removal, or similar interference. Abstract possibilities of scripts alone do not return the case to needs review. [Our interpretation: native-element default assessment. Supporting evidence: 2.1.1-E02–E03]
- Check custom/repurposed components using their provided keyboard interface. For nonfocusable composite containers, assess their items without duplicating unresolved judgments; retain container checks for activedescendant or unknown mechanisms. An unfocusable dialog container alone does not fail. [Our interpretation: assessment-unit policy. Evidence: 2.1.1-E01, E04]
- Exclude elements where effective disabled behavior blocks browser operation. Do not exclude from aria-disabled or disabled on a/div alone. Evaluate functions in their available states when they become enabled. [Our interpretation: excluding states nobody can operate. Supporting evidence: 2.1.1-E01]
- Reached results from keyboard-reachability-check establish access. Unreachable is a candidate requiring equivalent-path review; retain not-evaluated/aborted evidence. Grid/treegrid, iframes, Shadow DOM, and unexpanded states may be outside coverage. [Our interpretation: tool mapping. Implementation checked: `packages/a11y-audit/src/playwright/runKeyboardReachabilityCheck.ts`, `src/utils/axe-format.ts`]

## Judgment examples

- **Conformant:** A search button is not Tab-reachable, but Enter in the search field performs the same search. [Evidence: 2.1.1-E01–E02]
- **Non-conformant:** Reordering requires dragging, with no movement buttons or keyboard alternative. Do not exempt changing endpoints as path-dependent. [Evidence: 2.1.1-E01–E03]
- **Do not flag under the exception:** Freehand drawing captures the stroke path itself. Continue evaluating color selection, saving, and other functions. [Evidence: 2.1.1-E01; surrounding-function application is an author inspection example]
- **Do not flag:** A custom button works with Enter but not Space. APG deviation alone does not fail. [Evidence: 2.1.1-E04]
- **Needs review:** The tool did not reach an element, but instructions list a shortcut. Verify its result. [Our interpretation: inspection example. Evidence: 2.1.1-E01–E02]

## When building

- Prefer native elements and familiar key interactions, providing keyboard execution of the same functions. [Evidence: 2.1.1-E02, E04]
- Prefer tabindex 0/-1 and consult APG for composites. This recommendation does not make positive tabindex or unconventional keys alone 2.1.1 failures. [Our interpretation: implementation recommendation. Supporting evidence: 2.1.1-E04]

## When checking

- **Settled:** Functional results checked against exceptions and alternatives. Reachability evidence establishes access only. [2.1.1-E01–E04]
- **Remains:** Activation, value changes, opening/closing, custom keys, and untested states/components.
- **Do not assert:** Universal requirements for every control's Tab access, both Enter and Space, or exact APG conformance. [Evidence: 2.1.1-E01, E04]
