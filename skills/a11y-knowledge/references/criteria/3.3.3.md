# 3.3.3 Error Suggestion

- Components in scope: form
- Inputs needed: the screen in its error state
- Automated checks: none

## Rationale

- [Understanding 3.3.3](https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html) ([Japanese translation](https://waic.jp/translations/WCAG22/Understanding/error-suggestion.html))
  - If an input error is automatically detected and a correction is known, show it to the user.
  - The exception is when it would jeopardize security or purpose (showing the correct password value).
  - "Required" alone may not count as a correction suggestion (it is not clear what to enter). For a format error, show an example of the correct format.
- [G84: describing the error](https://www.w3.org/WAI/WCAG22/Techniques/general/G84), [G85: showing the correct format](https://www.w3.org/WAI/WCAG22/Techniques/general/G85), [G177: showing correction candidates](https://www.w3.org/WAI/WCAG22/Techniques/general/G177)

## Judgment lines

- As with 3.3.1, if the error state does not appear in the information, needs review. Do not mark non-conformant because the correction suggestion mechanism cannot be confirmed. [Understanding]
- On a screen showing errors, if there is only the description of the error and no way to correct it ("Invalid value"), non-conformant only when a correction is known. [Understanding]

## When building

- Write in the error message what is wrong and how to fix it ("Enter the postal code as 7 digits (for example, 1000001)").
- For errors with determinable candidates (spelling variants of prefecture names), show the candidates.
- For password errors, do not show the correct value (exception).

## When checking

- **Settled**: none.
- **Remains**: actually submit with incorrect input and check whether a way to correct it is shown.
- **Do not assert**: do not mark conformant or non-conformant from the screen before input alone.
