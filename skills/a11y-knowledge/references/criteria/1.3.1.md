# 1.3.1 Info and Relationships

- Components in scope: input fields (input, checkbox, radio, switch, combobox, listbox, slider), landmarks, navigation, form, table, heading, list, modal, and many others
- Inputs needed: accessibility tree (source of the name, parent-child relationships), visible labels and headings on screen
- Automated checks: axe `label`, `list`, `th-has-data-cells`, `landmark-*`, and so on

## Rationale

- [Understanding 1.3.1](https://www.w3.org/WAI/WCAG22/Understanding/info-and-relationships.html) ([Japanese translation](https://waic.jp/translations/WCAG22/Understanding/info-and-relationships.html))
  - The axis of judgment is "can the structure and relationships conveyed visually also be determined programmatically (or are they written in text)". It does not require creating relationships that are not there visually.
  - "Programmatically determinable" means a form assistive technology can read: name association, heading hierarchy, table header cells, list markup.
- [H44: label element](https://www.w3.org/WAI/WCAG22/Techniques/html/H44), [ARIA16: aria-labelledby](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA16), [ARIA11: landmarks](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA11), [F68: label not associated](https://www.w3.org/WAI/WCAG22/Techniques/failures/F68)

## Judgment lines

### Input fields and labels

- If there is visible label text on screen but it is not programmatically associated, non-conformant. [Understanding] (F68)
- If associated via `label for` / wrapping with a label / `aria-labelledby`, conformant. [Understanding]
- If an input field has no name and text that serves as a label is visible near it, judge it not associated and mark it non-conformant. Associated label text would become the name, so the missing name is itself evidence that the label is not associated (do not hold it as "association unknown"). [Our interpretation]
- If there is no text on screen that serves as a label (placeholder only), there is no relationship to associate, so it is out of scope for 1.3.1. The absence of a label, or having only a placeholder, is handled under 3.3.2. [Our interpretation]
- A name that comes from the placeholder is still a name. Do not use it as a reason for non-conformance under 1.3.1 / 4.1.2. [Our interpretation]

### Landmarks

- main / navigation / complementary / banner / contentinfo / search are conformant in principle even without a name. Do not mark non-conformant solely because there is no name. [Understanding]
- A `<section>` without a name is a plain section that does not become a region landmark, so the absence of a name is not a reason for non-conformance. If `role="region"` is explicit, a name is required. [Understanding] (a region becomes a landmark only when it has a name)
- When there is a name, check that it matches the heading inside the region or the region's meaning (the heading says "Billing information" but `aria-labelledby` points to "Account settings"). If it cannot be confirmed, do not mark non-conformant by guesswork. [Our interpretation]
- Whether multiple landmarks of the same type have distinguishing names cannot be known without looking at the whole page. Do not mark non-conformant from the information of a single element. [Our interpretation]

### Forms (container)

- 1.3.1 for a form is checked on the structure of the form as a container (grouping, relationship to headings). Problems with the input fields inside (no name, label not associated) are handled under that input field's 1.3.1 / 4.1.2 and the form's 3.3.2, and the form's 1.3.1 is not additionally marked non-conformant (do not double count). [Our interpretation]

### Dialogs

- Treat a missing name on dialog / alertdialog itself as a best-practice improvement candidate under the [4.1.2 author policy](./4.1.2.md). Do not reassign it as a 1.3.1 failure. Identify specific evidence when reporting a separate structure or relationship issue under 1.3.1. [Our interpretation]

## When building

- Associate visible labels with `<label for>`. When a `<label>` cannot be placed for visual reasons, point to the visible text with `aria-labelledby`.
- Group input fields that look grouped (three address fields, a row of radios) with `<fieldset>` and `<legend>`.
- Mark up headings as `h1` to `h6` according to the visual hierarchy. Do not create bold paragraphs that look like headings.
- When placing two or more landmarks of the same type, give distinguishing names with `aria-label` or `aria-labelledby`.
- Name a `<section>` only when you want it to be a landmark. An unnamed section does not become a landmark.
- Express table headers with `<th>` (and `scope` if needed). Do not create tables for layout.

## When checking

- **Settled**: violations of axe `label` (an input field not associated with its visible label), `list` / `listitem`, `th-has-data-cells`, and so on are non-conformant.
- **Remains**: whether the heading hierarchy matches the visual one, whether grouping matches the visual one, whether landmark names match their content. Decide by looking at the whole page.
- **Do not assert**: do not mark non-conformant solely because a landmark has no name. Do not mark a placeholder-only field non-conformant under 1.3.1 (check under 3.3.2).
