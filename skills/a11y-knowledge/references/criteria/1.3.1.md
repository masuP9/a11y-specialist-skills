# 1.3.1 Info and Relationships

- Components in scope: inputs (input, checkbox, radio, switch, combobox, listbox, slider), landmarks, navigation, form, table, heading, list, modal, and others
- Inputs needed: accessibility tree and DOM (name sources, parent-child relationships), structures and relationships conveyed visually or audibly
- Automated checks: axe `list` / `listitem`, `th-has-data-cells`, and similar rules are partial checks; see below for `label` and `landmark-*` classification
- Sources checked: 2026-11-02. WCAG is the 2024-12-12 Recommendation; WAI-ARIA 1.2 is the 2023-06-06 Recommendation; Understanding / Techniques are living public pages. This review focuses on HTML, not every medium or document format. The following are summaries, not quotations.

## Rationale

### 1.3.1-E01 — Compare specific relationships conveyed through presentation

- **Type / source:** [Normative — Info and Relationships](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#info-and-relationships), [Understanding — Intent](https://www.w3.org/WAI/WCAG22/Understanding/info-and-relationships.html#intent).
- **Summary:** Check whether structures/relationships conveyed visually or audibly are programmatically available or provided in text. This does not require adding relationships that do not exist.
- **Conditions / limits:** Text such as “Required fields are marked *” can convey relationships. Do not treat every decoration as structure; identify the information lost.

### 1.3.1-E02 — Separate visible-label relationships from name presence

- **Type / source:** [Technique — H44, Tests](https://www.w3.org/WAI/WCAG22/Techniques/html/H44#tests), [ARIA16, Tests](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA16#tests) (Sufficient for identifying relationships). [Failure — F68](https://www.w3.org/WAI/WCAG22/Techniques/failures/F68.html#tests) currently maps to 4.1.2.
- **Summary:** Inspect label/ARIA implementation and name sources to establish the relationship between a visible label and its control. H44 and ARIA16 are not the only methods.
- **Conditions / limits:** Do not transfer F68 or name-check results directly to 1.3.1. Having a name does not establish correspondence for every relationship presented on screen.

### 1.3.1-E03 — Verify heading, list, and input-group semantics

- **Type / source:** [Technique — H42, Description / Tests](https://www.w3.org/WAI/WCAG22/Techniques/html/H42#tests), [H48, Description / Tests](https://www.w3.org/WAI/WCAG22/Techniques/html/H48#tests), [H71, Description / Tests](https://www.w3.org/WAI/WCAG22/Techniques/html/H71#tests) (Sufficient for identifying structure/relationships).
- **Summary:** Compare implemented semantics with headings, lists, and input groups sharing an explanation. Fieldset/legend is one way to convey a group's description. H71 does not require it when individual labels and clear instructions sufficiently describe the choices.
- **Conditions / limits:** Do not require list markup for every comma-separated list in a sentence. Identify lost hierarchy/relationships instead of failing solely for particular heading numbers or missing fieldset.

### 1.3.1-E04 — Distinguish table associations from layout purposes

- **Type / source:** [Technique — H63, Description / Tests](https://www.w3.org/WAI/WCAG22/Techniques/html/H63#tests) (Sufficient), [Failure — F46, Description / Tests](https://www.w3.org/WAI/WCAG22/Techniques/failures/F46#tests).
- **Summary:** Check whether data cells expose the necessary headers. Simple tables with headers in the first row/column can use th alone. Distinguish falsely assigning data-table semantics to layout tables.
- **Conditions / limits:** Do not require scope for every table. Layout-table use alone is not a WCAG failure; check actual false structure, reading-order issues, and similar problems.

### 1.3.1-E05 — Distinguish region meaning from ARIA naming requirements

- **Type / source:** [Technique — ARIA11, Description / Tests](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA11#tests) (Sufficient), [Technical specification — WAI-ARIA 1.2, region](https://www.w3.org/TR/2023/REC-wai-aria-1.2-20230606/#region).
- **Summary:** Landmarks identify regions. An explicit region requires a name expressing its content's purpose. Check named regions against their presented content.
- **Conditions / limits:** Do not equate ARIA implementation requirements with WCAG failure conditions. Unnamed main or similar landmarks, or repeated landmark types, do not uniformly fail 1.3.1.

## Judgment lines

### Input fields and labels

- Visible label text without a programmatic association fails. [Evidence: 1.3.1-E01–E02]
- Correct relationships through `label for`, wrapping labels, or `aria-labelledby` conform for that relationship. [Evidence: 1.3.1-E02]
- When a nameless control has nearby visible text serving as its label, judge the missing association as non-conformant. The text would supply its name if associated; confirmed absence of the computed name is evidence of the missing relationship. Do not defer as “association unknown.” [Our interpretation: author inspection/reporting policy. Supporting evidence: 1.3.1-E01–E02]
- With no visible label text (placeholder only), there is no external label relationship to associate; do not flag its absence under 1.3.1. Evaluate other relationships such as grouping separately. Missing labels/placeholder-only cases belong under 3.3.2. [Our interpretation: author inspection/reporting policy. Supporting evidence: 1.3.1-E01–E02]
- A name from a placeholder is still a name. Do not use that origin as a reason for failure under 1.3.1 / 4.1.2. [Our interpretation: author inspection/reporting policy. Supporting evidence: 1.3.1-E01–E02]

### Landmarks

- Main / navigation / complementary / banner / contentinfo / search generally conform without names. Do not fail solely for missing names. [Evidence: 1.3.1-E05]
- An unnamed `<section>` remains a plain section rather than a region landmark; its missing name is not a failure. An explicit `role="region"` needs a name. [Evidence: 1.3.1-E05; naming is an ARIA requirement, while a 1.3.1 failure needs an identified lost relationship]
- Check any name against the region's heading/meaning, such as “Billing information” incorrectly referencing “Account settings.” Do not fail by speculation when correspondence cannot be established. [Our interpretation: author inspection/reporting policy. Supporting evidence: 1.3.1-E01, E05]
- Distinguishing names for repeated landmark types requires inspecting the whole page. Do not fail from a single element's information. [Our interpretation: author inspection/reporting policy. Supporting evidence: 1.3.1-E01, E05]

### Forms (container)

- Evaluate the form container's grouping and heading relationships. Attribute inner-field naming/association problems to those fields' 1.3.1 / 4.1.2 and the form's 3.3.2, without duplicating a failure on the form's 1.3.1. [Our interpretation: author inspection/reporting policy. Supporting evidence: 1.3.1-E01–E02]

### Dialogs

- Follow the [4.1.2 author policy](./4.1.2.md): missing names on dialog / alertdialog themselves are best-practice improvement candidates, not reassigned 1.3.1 failures. Give specific evidence for any separate structure/relationship problem. [Our interpretation: author inspection/reporting policy. Supporting evidence: 1.3.1-E01–E02]

## Judgment examples

- **Conformant:** A simple data table has th in the first row, with correct data/header associations. Do not flag missing scope alone. [Evidence: 1.3.1-E04]
- **Non-conformant:** A visually presented heading is only a bold paragraph, with no other provision of its heading meaning. [Evidence: 1.3.1-E01, E03]
- **Do not flag:** “Red, blue, green” is a list within a sentence; conversion to ul is not required. [Evidence: 1.3.1-E03]
- **Retain author policy:** Evaluate placeholder-only labels under 3.3.2 without failing their missing label relationship here; do not reassign a dialog's missing name to 1.3.1. [Our interpretation: existing division among criteria. Supporting evidence: 1.3.1-E01–E02]
- **Needs review:** The tree contains headings, but the screen was not captured and visual hierarchy correspondence is unknown. Compare the screen and DOM. [Our interpretation: inspection policy. Evidence: 1.3.1-E01, E03]

## When building

- Associate visible labels using `<label for>` or reference visible text with `aria-labelledby` when a label cannot be placed.
- Use fieldset/legend for visually grouped fields such as address fields or radio choices.
- Use h1–h6 to express the presented hierarchy rather than bold paragraphs resembling headings.
- Give repeated landmark types distinguishing names using `aria-label` or `aria-labelledby`.
- Name a section when it should be a landmark; unnamed sections are not landmarks.
- Use th and scope or other associations as needed. Prefer CSS for layout, without failing layout tables solely for their use. [Evidence: 1.3.1-E04]

## When checking

- **Settled:** Confirmed discrepancies between presented relationships and implementation. Also inspect target nodes/relationships for axe list / listitem and th-has-data-cells findings. [1.3.1-E01–E04]
- **Remains:** Heading hierarchy, table headers, input grouping, and region names/content. Trees alone cannot establish correspondence to visual/auditory presentation.
- **Do not assert:** axe-core 4.14.0 `label` checks 4.1.2 names and accepts placeholders; `landmark-*` rules are best practice. Do not transfer these directly to confirmed 1.3.1 failures. [Our interpretation: tool mapping. Implementation checked: `node_modules/axe-core/axe.js`. Evidence: 1.3.1-E01–E02, E05]
