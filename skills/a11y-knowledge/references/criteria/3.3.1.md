# 3.3.1 Error Identification

- Components in scope: form, input (client-side and server-side validation)
- Inputs needed: invalid input, validation results, error-state screen, text alternatives, and attributes
- Automated checks: no dedicated check. Do not judge from the initial screen alone
- Sources checked: 2026-11-02. WCAG is the 2024-12-12 Recommendation; Understanding / Techniques are living WCAG 2.2 public pages. The following are summaries, not quotations.

## Rationale

### 3.3.1-E01 — Evaluate automatically detected input errors

- **Type / source:** [Normative — Error Identification](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#error-identification), [Understanding — Intent](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html#intent).
- **Summary:** For a detected error, check for text identifying the item and describing what is wrong. Automatically correcting an out-of-range value also requires an explanation of the change.
- **Conditions / limits:** Distinguish not validating from rejecting input without an explanation. The latter is not inapplicable. Check correction guidance under [3.3.3](./3.3.3.md).

### 3.3.1-E02 — Do not prescribe a single error location

- **Type / source:** [Technique — G83, Description](https://www.w3.org/WAI/WCAG22/Techniques/general/G83#description), [G85, Description](https://www.w3.org/WAI/WCAG22/Techniques/general/G85#description) (both Sufficient for 3.3.1).
- **Summary:** Missing input or format errors can be explained beside fields, in a summary, or in a dialog. Check whether users can identify which field has which problem.
- **Conditions / limits:** A summary and links to individual fields are not the only methods. Red borders alone or icons without explanations are insufficient.

### 3.3.1-E03 — Separate attributes from adequate descriptions

- **Type / source:** [Technique — ARIA21, Description and Tests](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA21#tests) (Sufficient), [Understanding — Intent](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html#intent).
- **Summary:** ARIA21 sets state according to validation results and communicates errors with labels and descriptions. Do not set `aria-invalid="true"` before validation. The attribute itself is not a normative requirement.
- **Conditions / limits:** Its presence does not establish an adequate explanation; its absence does not establish a 3.3.1 failure. Evaluate text alternatives too. Native HTML validation can conform when it communicates the item and error in the supported environment, without automatically satisfying 3.3.3.

## Judgment lines

- Text or a text alternative identifying the detected error's item and nature satisfies this condition. If the error state has not been obtained, mark needs review and specify the input and actions needed to reproduce it. [Evidence: 3.3.1-E01–E03]
- Do not fail solely for placement, missing specific ARIA attributes, or a missing error summary. For issues with associations, states, or notifications, separately check the applicability of 1.3.1 / 4.1.2 / 4.1.3. [Evidence: 3.3.1-E02–E03]

## Judgment examples

- **Conformant:** The server returns “The email address format is incorrect,” identifying the relevant field. Assess correction guidance separately under 3.3.3. [Evidence: 3.3.1-E01–E02]
- **Non-conformant:** Submission is rejected with red borders only and no text alternatives. Also report missing explanations when an out-of-range quantity is silently changed to the maximum. [Evidence: 3.3.1-E01–E03]
- **Do not flag:** Missing custom `aria-invalid` alone when native validation communicates the item and error. [Evidence: 3.3.1-E03]
- **Needs review:** Only the initial screen is available; responses to empty submission or server validation have not been examined. Obtain those states. [Our interpretation: inspection policy. Evidence: 3.3.1-E01]

## When building

- Prefer associated descriptions beside fields, with a summary and field links for multiple errors. This is a recommended implementation, not the only conforming method. [Our interpretation: helping users reach corrections. Evidence: 3.3.1-E02–E03]
- Update states and descriptions after validation; remove stale errors after correction. [Evidence: 3.3.1-E03]

## When checking

- **Settled:** Results of comparing detected errors with descriptions identifying their items and nature. [3.3.1-E01–E03]
- **Remains:** Server responses, automatic correction, and native validation presentation in supported environments. Test invalid input where submission side effects are acceptable.
- **Do not assert:** Conformance or failure from initial static checks or ARIA attributes alone. [Our interpretation: inspection policy]
