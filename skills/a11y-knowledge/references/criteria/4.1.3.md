# 4.1.3 Status Messages

- Scope: Result, waiting, progress, and error notifications presented without a change of context
- Materials: Trigger, before/after display and focus, DOM/notification implementation, and assistive-technology output in the target environment
- Automated check: Static trees and ARIA syntax checks alone cannot verify notifications
- Sources checked: 2026-11-02. WCAG: Recommendation of 2024-12-12; Understanding / Techniques: living published pages. The following are summaries, not quotations.

## Evidence

### 4.1.3-E01 — Do not treat every dynamic update as a status message

- **Type / source:** [Normative — Status Messages](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#status-messages), [Understanding — Intent / Examples](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html#intent).
- **Summary:** Separate search results themselves from result counts/completion/no-results messages. Changes of context, such as a dialog taking focus, are outside this criterion's status messages.
- **Conditions / limits:** Merely expanding accordions, switching tabs, or adding questions does not require creating a status message. Separate component-state exposure under 4.1.2.

### 4.1.3-E02 — Check notification mechanisms and content

- **Type / source:** [Technique — ARIA22 “Description / Tests”](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA22#description) (for 4.1.3, combined with applicable specific techniques such as G199; with G193 for progress), [ARIA19 “Description / Tests”](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA19#description) (for 4.1.3, combined with applicable specific techniques such as G83), [ARIA25 “Example / Tests”](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA25#tests) (Sufficient).
- **Summary:** Check the mechanism communicating updates and notification content including necessary context. `progressbar` values alone do not establish notifications outside focus.
- **Conditions / limits:** Insertion into existing containers in ARIA22/ARIA19 is one sufficient approach. Do not universally require particular roles or `aria-live` attributes. Include context when a number alone does not convey what changed.

### 4.1.3-E03 — Do not immediately fail missing attributes

- **Type / source:** [Failure — F103 “Description / Tests”](https://www.w3.org/WAI/WCAG22/Techniques/failures/F103#description), [Technique — ARIA27 “Description / Tests”](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA27#description) (Sufficient, with support caveats).
- **Summary:** First establish that content is a status message, then inspect HTML mechanisms, roles, properties, and other notification means. F103 includes confirming that assistive technology does not expose the status information.
- **Conditions / limits:** Consider API notifications too. ARIA27's April 2026 support note recommends `ariaNotify` as progressive enhancement alongside more reliable techniques. An API call alone does not establish support in the target environment.

### 4.1.3-E04 — Check changes, removal, and non-text content too

- **Type / source:** [Understanding — Examples of status messages that do not add new text to the screen](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html#examples-of-status-messages-that-do-not-add-new-text-to-the-screen).
- **Summary:** Include count changes, completion conveyed by disappearing waiting indicators, and status icons/sounds. Non-visible notifications may convey equivalent information.
- **Conditions / limits:** Do not restrict inspection to new DOM nodes or visible text. If waiting ends with a context change, account for that change.

## Judgment lines

- Pass when relevant status information is available for assistive technology to present without moving focus. Fail when applicability and an inadequate notification mechanism preventing communication are confirmed. [Evidence: 4.1.3-E01–E03]
- Neither `role="status"` nor readable text in a static tree alone establishes Pass. Distinguish discovering content by navigating to it from update notifications. [Evidence: 4.1.3-E02–E03]
- Do not immediately treat AT preference-based delay/suppression as an author defect. Record the author's mechanism, target environment, operation, and output. [Evidence: 4.1.3-E01. Recording policy is ours]
- Do not fail the absence of newly created notifications for search results or additional question fields. Existing result counts and waiting indicators do require assessment as status information. [Evidence: 4.1.3-E01, E04]

## Judgment examples

- **Pass:** A cart update communicates “Shopping cart, three items” without moving focus. [Evidence: 4.1.3-E02]
- **Out of scope:** Focus moves to an error dialog and its content is presented. Do not universally require an additional live notification. [Evidence: 4.1.3-E01]
- **Do not flag under this SC:** An answer adds question fields without a separate status message. [Evidence: 4.1.3-E01]
- **Fail:** “Zero results” appears without a notification mechanism; AT users must navigate to that location to discover it. [Evidence: 4.1.3-E03]
- **Needs review:** Progress values are available but notification output is not. Check separate live regions/APIs and output while focus remains elsewhere. [Our interpretation: inspection example. Evidence: 4.1.3-E02–E03]

## When building

- Choose a mechanism appropriate to the message and verify that actual updates communicate necessary context. Do not assume value updates or merely removing a waiting indicator suffice. [Evidence: 4.1.3-E02–E04]
