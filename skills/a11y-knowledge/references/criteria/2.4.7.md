# 2.4.7 Focus Visible

- Scope: User interfaces operated by keyboard
- Needed: Keyboard presentation, continued visibility, and screenshots/video where needed
- Automated checks: focus-indicator-check (computed-style differences, optional image differences)

- Sources checked: 2026-11-01. WCAG: 2024-12-12 Recommendation; Understanding / Techniques: live WCAG 2.2 pages. The following are summaries, not quotations.

## Rationale

### 2.4.7-E01 — Check a visible keyboard mode and continued visibility

- **Type / source:** [Understanding — Intent](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html#intent).
- **Summary:** A mode with visible keyboard focus is required. The indicator must not disappear on a time limit. Showing it during pointer interaction is best practice.
- **Conditions / limits:** Absence of a ring on mouse click alone is not a failure. An immediate screenshot cannot establish whether the indicator later disappears.

### 2.4.7-E02 — An outline is not the only form of indication

- **Type / source:** [Technique — G149, Tests](https://www.w3.org/WAI/WCAG22/Techniques/general/G149#tests), [C15, Examples / Tests](https://www.w3.org/WAI/WCAG22/Techniques/css/C15#tests) (both Sufficient).
- **Summary:** Native UA indicators can be used. C15 also illustrates background changes and highlighting an adjacent label.
- **Conditions / limits:** Do not require a custom outline or a style change on the focused element itself. Check whether highlighting another element identifies the focused component. Attributes/styles alone do not prove visibility.

### 2.4.7-E03 — Check loss of indication, not just removal of outline

- **Type / source:** [Failure — F78, Description / Tests](https://www.w3.org/WAI/WCAG22/Techniques/failures/F78#tests).
- **Summary:** Removing or making the default indicator invisible without a visible replacement meets the failure condition. A drawn indicator may still be indistinguishable from its surroundings.
- **Conditions / limits:** Do not fail solely for `outline: none`. Check visibility during keyboard focus, including replacement indicators.

### 2.4.7-E04 — Keep shape and contrast requirements separate

- **Type / source:** [Understanding — References to 1.4.11 / 2.4.13 in Intent](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html#intent).
- **Summary:** 2.4.7 does not specify indicator shape. Non-text focus indicators also relate to 1.4.11; indicator area and other requirements relate to 2.4.13.
- **Conditions / limits:** Do not require a full perimeter or two sides under 2.4.7. Check component obscuration separately under 2.4.11.

## Judgment lines

- Judge from observed keyboard focus movement. Without measurement, leave for review. [Our interpretation: existing evaluation policy; supporting evidence: 2.4.7-E01–E03]
- No style difference alone does not establish failure. Check pseudo-elements, parents, adjacent elements, and other indicators. An image difference also needs verification that it represents focus indication. [Our interpretation: tool-result handling; supporting evidence: 2.4.7-E02, 2.4.7-E03]
- If every target has a style change, measurement completed, and none were skipped, retain the existing operational pass for that inspected scope. State that this does not directly prove visibility or persistence and that color-difference magnitude is unverified. Return suspected disappearance or indistinguishability to review. [Our interpretation: author’s measurement policy; limits: 2.4.7-E01, 2.4.7-E03]
- Fail when actual presentation establishes an unidentifiable focus location or time-limited disappearance. Distinguish this from the policy against failure based on automated checks alone. [Evidence: 2.4.7-E01, 2.4.7-E03]

## When building

- Preserve the default indicator or provide an identifiable replacement using `:focus-visible` or another method. [2.4.7-E01–E03]
- Recommend easy-to-locate indicators, such as a full perimeter or two sides, rather than relying only on background color. This is our implementation policy; other shapes or background changes alone can satisfy 2.4.7. [Our interpretation: author recommendation; supporting evidence: 2.4.7-E02, 2.4.7-E04]

## When checking

- **Conclusive:** Invisibility or disappearance verified in actual presentation. Automated style differences alone are inconclusive. [2.4.7-E01, 2.4.7-E03]
- **Remaining:** `visualDiff` from `screenshotDiff` is optional supporting information. Animations can create differences; zero differences do not exclude indicators outside the comparison area. [Our interpretation: tool limits; implementation: [axe-format.ts](../../../../packages/a11y-audit/src/utils/axe-format.ts)]
- **Do not overclaim:** Do not pass interrupted traversal, skipped targets, or zero targets. Initial-state measurement does not cover other display states. [Our interpretation: inspection scope management]
