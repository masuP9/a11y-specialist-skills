# アクセシビリティ デザインレビュー ガイド

[English](./design-review.md)

実装前のデザイン（モックアップ・ワイヤーフレーム・UI仕様）を見て、アクセシビリティの問題を見つけるガイド。

## 必要な能力

- Figma URL、デザイン仕様書、関連ドキュメントを取得する
- デザイン仕様書と、環境が対応する画像・PDFなどの視覚資料を読み取る
- Figma を読む手段（MCP など）があれば、それで塗り・変数（色のトークン）・寸法・テキストスタイルを取得する。画像から推定するより正確

## レビュープロセス

### ステップ1: デザインを理解

```
1. 成果物タイプを特定: Figma、画像、PDF、仕様ドキュメント
2. 目的を理解: コンポーネント/ページ機能とユーザーフロー
3. インタラクティブ要素をマップ: ボタン、フォーム、ナビゲーション、モーダル
4. 状態を記録: デフォルト、ホバー、フォーカス、アクティブ、無効、エラー
```

### ステップ2: 視覚分析

次の観点で問題を探す：

**ビジュアルを調査：**
- **色とコントラスト**: テキスト/背景コントラスト、UIコンポーネントコントラスト、色のみのインジケーター
- **タイポグラフィ**: フォントサイズ、行の高さ、行の長さ、画像内のテキスト
- **タッチターゲット**: サイズ（AA の 2.5.8 は 24×24px 以上、または間隔の例外。44×44px は AAA の 2.5.5）、インタラクティブ要素間の間隔
- **視覚階層**: 見出しの明確さ、情報のグループ化、アイコンのみの要素
- **フォーカス状態**: 視覚的なフォーカスインジケーター、コントラスト要件
- **フォームデザイン**: 視覚的なラベル（プレースホルダーのみではない）、エラー表示パターン
- **レスポンシブ**: モバイルタッチターゲット、フォントスケーリング、レイアウト

重大度は [SKILL の「重大度」](../SKILL.ja.md#重大度) の表で付ける。

### ステップ3: 質問と手動チェックをフラグ

- **コントラスト比**: 色の値（16進など）が分かれば比を計算し、結果を指摘に書く。画像からの推定しかできないときだけ、色のペアを記録して要確認にする

デザインからは決まらないので、質問にまとめるもの：
- **フォーカス管理**: キーボードナビゲーションフローについて質問
- **動的挙動**: 状態変化、アナウンスについて質問
- **代替コンテンツ**: altテキスト仕様について質問

## 出力フォーマット

### デザイン概要
```
デザイン: ホームページリデザイン（Figma）
範囲: デスクトップとモバイルビュー
レビューしたコンポーネント: ヘッダー、ヒーロー、機能カード、フッター
```

### 良い点
```
- **Good**: 大きな見出しと豊富な間隔による明確な視覚階層
- **Good**: 一貫したフォーカスインジケーターデザインが指定されている（青いアウトライン、3px）
- **Good**: すべてのフォームフィールドに入力の上に視覚的なラベルがある
- **Good**: モバイルデザインのタッチターゲットが44×44px以上（2.5.8 の 24px を満たし、AAA の 2.5.5 も満たす）
```

### 問題点（重要度別）

**Critical（致命的）** - アクセス障壁を作成

```
- **箇所**: フォームエラー状態（フレーム7）
- **問題**: エラー表示が赤い枠のみを使用、アイコンやテキストなし
- **WCAG**: 1.4.1 色の使用 (A)
- **影響**: 色覚特性のあるユーザーや画面を見ていないユーザーが、どの欄がエラーか分からない
- **推奨事項**: エラーアイコンと、欄ごとの「エラー：」で始まるメッセージを追加
```

**Major（重大）** - 困難を作成する可能性

```
- **箇所**: 主ボタン（フレーム2、16px・通常の太さ）
- **問題**: #0088FF上の#FFFFFFのテキストのコントラスト比が 3.52:1（4.5:1 未満）
- **WCAG**: 1.4.3 コントラスト（最低限） (AA)
- **影響**: ロービジョンのユーザーがボタンの文字を読みにくい
- **推奨事項**: 背景を #0066CC（5.57:1）程度まで暗くする
```

**Minor（軽微）** - ベストプラクティスの改善

```
- **箇所**: 本文テキスト（タイポグラフィ仕様）
- **問題**: 行の高さ1.3。WCAG AA の要件ではない（1.4.12 は利用者が行の高さを変えたときに崩れないことを求める基準で、作者が指定する値は問わない）
- **WCAG**: 該当なし（ベストプラクティス。AAA の 1.4.8 は 1.5 以上を求める）
- **影響**: ディスレクシアのあるユーザーの可読性を低下させる可能性
- **推奨事項**: 可読性向上のため行の高さを1.5に増やす
```

### デザインチームへの質問

```
1. **フォーカス管理**: モーダルを開く/閉じるときフォーカスはどう移動すべきか？
2. **状態ごとの色**: ホバー・押下・無効のときのボタンの色は？（コントラスト比を計算するため）
3. **代替テキスト**: ヒーロー画像のaltテキストは何にすべきか？
4. **読み込み状態**: 「もっと読み込む」ボタンの読み込み状態はどう示されるか？
5. **キーボードナビゲーション**: ユーザーはキーボードで画像カルーセルをどうナビゲートするか？
```

### 実装への推奨事項

```
1. **ARIA仕様を文書化**
   - カスタムドロップダウン: role="combobox"、aria-expanded状態
   - モーダルダイアログ: role="dialog"、aria-labelledby
   - タブ: role="tablist"、aria-selected状態

2. **アクセシビリティ注釈レイヤーを作成**
   - 見出しレベルをマーク（H1、H2、H3）
   - ランドマーク領域にラベル付け（nav、main、aside）
   - 複雑なインタラクションのタブ順序を指定

3. **コントラスト検証チェックリスト**
   - 開発者テスト用の色ペアを提供
   - 境界線上のコントラスト比をフラグ
   - フォーカスインジケーターのコントラスト要件を指定

4. **代替コンテンツ仕様**
   - すべての情報を持つ画像のaltテキスト
   - ビデオコンテンツのトランスクリプト計画
   - チャートのデータテーブル代替
```

## 重要な原則

- **色は値で計算する**: 色の値が取れればコントラスト比を計算する。画像からの推定は要確認にとどめる
- **質問する**: デザインは動的挙動を示さない - どう動作するか質問
- **必要事項を注釈**: 開発者が実装する必要があるものを指定（ARIAロール、altテキスト）
- **問題を予防**: コードが書かれる前にアクセシビリティ問題を捕捉
- **具体的に**: デザインから実際のフレーム、色、測定値を参照

**注意**: 実装ではなくデザインの意図を見ている。見た目で決まることは指摘し、実装で決まること（ARIA、フォーカスの動き、読み上げ）は開発者向けの仕様として書き出す。
