# アクセシビリティレビュー

ユーザーがレビューを希望する対象を特定し、対応する参照ガイドに従ってアクセシビリティレビューを実行します。

## ステップ1: レビュー対象の特定

ユーザーのリクエストを分析してレビュー対象を判別します：

### Webページ（実際のURL）
**判別指標：**
- ユーザーが`http://`または`https://`で始まるURLを提供
- ユーザーが「このページをチェック」「このサイトをレビュー」「このURLをテスト」と言う
- デプロイ済み/実際のウェブサイトをレビューしたい

**アクション:** ページレビューガイドに従う

### コード実装
**判別指標：**
- ユーザーがファイルパス（`.jsx`、`.tsx`、`.vue`、`.html`、`.js`など）を提供
- ユーザーが「このコンポーネントをレビュー」「コードをチェック」「この実装を見て」と言う
- コードベース内の特定のファイルやディレクトリに言及
- 静的コード解析について尋ねる

**アクション:** コードレビューガイドに従う

### デザインモックアップ/仕様書
**判別指標：**
- ユーザーがFigma URL（figma.com/file/...）を提供
- 画像ファイル（デザインの.png、.jpg、.pdf）を共有
- ユーザーが「このデザインをレビュー」「このモックアップをチェック」「このワイヤーフレームを見て」と言う
- デザイン仕様書や視覚的アクセシビリティについて尋ねる

**アクション:** デザインレビューガイドに従う

### 曖昧なケース
不明な場合は、ユーザーに尋ねます：
```
以下のアクセシビリティレビューができます：
1. **実際のWebページ**（URLを提供） - レンダリングされたページをテストします
2. **コード実装**（ファイルパスを提供） - ソースコードを分析します
3. **デザインモックアップ**（Figma URLまたは画像を提供） - 視覚デザインをレビューします

どれをレビューしますか？
```

## ステップ2: 知識ベースで線引きを引く

対象を特定したら、コードやページを見る前に、[a11y-knowledge](../a11y-knowledge/SKILL.ja.md) で指摘の線引きをそろえます。

1. 対象に出てくる部品を ARIA の役割（button、dialog、combobox など）で挙げる。
2. [index-by-component.ja.md](../a11y-knowledge/references/index-by-component.ja.md) で、役割ごとに問われる達成基準を引く。レイアウトやページ全体を見るときは [index-by-criterion.ja.md](../a11y-knowledge/references/index-by-criterion.ja.md) の「ページ全体」「複数ページ」も引く。
3. 引いた達成基準ごとに `../a11y-knowledge/references/criteria/<番号>.ja.md` の「線引き」と「作るとき」を読んでから、指摘を書く。「線引き」で適用しないとされているものを指摘しない。
4. **[独自]** の線引き（運用上の解釈）に基づいて指摘するときは、指摘にその旨を書き添える（例:「[独自] の線引き。プロジェクトの判断で上書き可」）。**[解説書]** の線引きは書き添え不要。

知識ベースは `../a11y-knowledge/` の相対パスで引きます。プラグインとして入れていれば届きます。スキルのディレクトリ単位のシンボリックリンクで入れているときは `a11y-knowledge` も一緒にリンクしてください。届かないときはこのステップを飛ばし、レポートに「知識ベース未参照」と書きます。

## ステップ3: 参照ガイドの読み込みとレビュー

対象を特定したら、ユーザーの言語に合う参照ガイドを読み、その手順をこのエージェントが直接実行します。

### Webページの場合
```
ページレビューガイドを読む：
- 英語: references/page-review.md
- 日本語: references/page-review.ja.md

ガイドに従って利用可能なブラウザ操作、Web取得、またはユーザー提供コンテンツを使い、ページをレビューする。
```

### コードの場合
```
コードレビューガイドを読む：
- 英語: references/code-review.md
- 日本語: references/code-review.ja.md

ガイドに従って対象ファイルと関連実装を調査し、コードをレビューする。
```

### デザインの場合
```
デザインレビューガイドを読む：
- 英語: references/design-review.md
- 日本語: references/design-review.ja.md

ガイドに従って利用可能な画像・文書・Figma取得手段を使い、デザインをレビューする。
```

### サブエージェントを使う場合

- ユーザーが並列レビュー、専門エージェントへの委譲、または複数対象の分担を明示した場合のみ使用する。
- 対象タイプごとに独立したエージェントへ分担し、各エージェントに該当ガイドと対象を渡す。
- すべての結果を待って重複を整理し、単一のレポートとして返す。
- サブエージェント機能がない環境では、このエージェントが順番にレビューする。

## ステップ4: 結果の返却

レビューが完了したら：
1. 発見事項をユーザーに提示
2. 必要に応じて追加対象のレビューを提案
3. 次のステップを提案（例：「次はコード実装をレビューしますか？」）

## 重要な注意事項

- **レビューを始める前に、必ず適切なガイドを読む**
- **言語を選択**（英語または日本語）ユーザーの言語に基づいて
- **証拠を明示** 何を確認でき、何を確認できなかったかを区別する
- **レビュータイプを混在させない** - 対象タイプごとに1つのガイドを使用する

## ワークフロー例

### 例1: ユーザーがURLを提供
```
ユーザー: 「https://example.com のアクセシビリティをレビューして」

1. 特定: これはWebページ（URL提供）
2. 線引き: index-by-component で達成基準を引き「線引き」「作るとき」を読む
3. 読み込み: references/page-review.ja.md
4. 実行: ガイドに従ってページを調査
5. 返却: 発見事項を提示
```

### 例2: ユーザーがファイルパスを提供
```
ユーザー: 「src/components/Button.tsx のa11y問題をチェックして」

1. 特定: これはコード（ファイルパス提供）
2. 線引き: index-by-component で達成基準を引き「線引き」「作るとき」を読む
3. 読み込み: references/code-review.ja.md
4. 実行: ガイドに従って対象と関連コードを調査
5. 返却: 発見事項を提示
```

### 例3: ユーザーがFigma URLを提供
```
ユーザー: 「このデザインをレビューして: https://figma.com/file/abc123」

1. 特定: これはデザイン（Figma URL）
2. 線引き: index-by-component で達成基準を引き「線引き」「作るとき」を読む
3. 読み込み: references/design-review.ja.md
4. 実行: ガイドに従ってデザインを調査
5. 返却: 発見事項を提示
```

## WCAG & 標準リファレンス

すべてのレビューは以下を参照すべきです：
- **WCAG 2.2**: https://www.w3.org/TR/WCAG22/
- **WCAG 2.2 日本語訳**: https://waic.jp/translations/WCAG22/
- **WAI-ARIA APG**: https://www.w3.org/WAI/ARIA/apg/
- **WCAG達成基準早見表**: https://www.w3.org/WAI/WCAG22/quickref/

よく参照する達成基準：
- 1.1.1 非テキストコンテンツ (A)
- 1.3.1 情報及び関係性 (A)
- 1.4.3 コントラスト（最低限） (AA)
- 2.1.1 キーボード (A)
- 2.4.6 見出し及びラベル (AA)
- 4.1.2 名前 (name)・役割 (role)・値 (value) (A)

注意: 証拠が不足する項目を推測で断定せず、手動確認として明示してください。
