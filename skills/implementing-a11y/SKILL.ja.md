# アクセシブルな実装

これから書く UI の部品に問われる達成基準を [a11y-knowledge](../a11y-knowledge/SKILL.ja.md) から引き、「線引き」と「作るとき」を読んでから実装する。このスキルは手順だけを持ち、知識は持たない。

- 書いたものを指摘してほしい → `reviewing-a11y`
- 達成基準ごとに Pass/Fail を付ける正式な監査 → `auditing-wcag`

> 知識ベースは `../a11y-knowledge/` の相対パスで引く。プラグインとして入れていれば届く。スキルのディレクトリ単位のシンボリックリンクで入れているときは、`a11y-knowledge` も一緒にリンクする。

## 手順

### 1. 書く部品を役割（role）で挙げる

実装しようとしている UI を、ARIA の役割で分ける（例: `dialog` と中の `button` と `textbox`）。見た目の名前（モーダル、トグル）ではなく役割で挙げる。

### 2. 部品に問われる達成基準を引く

[index-by-component.ja.md](../a11y-knowledge/references/index-by-component.ja.md) で、挙げた役割ごとに問われる達成基準を引く。

ページ全体・複数ページの達成基準（2.4.1、2.4.2、3.1.1、1.4.1、1.3.3、3.2.3、3.2.4、3.2.6）は部品には付かない。レイアウト・テンプレート・ページの骨格を書くときは [index-by-criterion.ja.md](../a11y-knowledge/references/index-by-criterion.ja.md) で「ページ全体」「複数ページ」の性質のものを引く。

### 3. 各達成基準の「線引き」と「作るとき」を読む

引いた達成基準ごとに `../a11y-knowledge/references/criteria/<番号>.ja.md` を開き、「線引き」と「作るとき」の 2 段だけ読む（「根拠」「確かめるとき」は実装には要らない）。全部を一度に読まない。

- **[解説書]** の線引きは、解説書（Understanding）に基づく。従う。
- **[独自]** の線引きは、運用上の解釈。プロジェクトの判断（設計ガイドライン、既存の部品の作り）で上書きしてよい。上書きしたら、その理由をコードのコメントか PR 本文に書き残す。

### 4. 作る

- 標準の HTML 要素で済むなら、それを使う（`<button>`、`<a href>`、`<input>`、`<dialog>`、`<details>`）。ARIA で役割を足すのは、標準の要素で作れないときだけ。
- 自作の部品は [WAI-ARIA APG](https://www.w3.org/WAI/ARIA/apg/patterns/) のパターン（キーボード操作・役割・状態）に合わせる。
- 「作るとき」の「避ける作り方」に当たっていないかを、書きながら見る。

### 5. 自己確認して、目視の分を残す

書いたものを、読んだ「作るとき」に照らして一度見直す。それから各達成基準の「確かめるとき」を開き、「言い切ってはいけないこと」（目視・操作でないと決まらないこと）に当たる箇所を、コードのコメントか PR 本文に「目視で確かめること」として残す。自分が確かめていないことを「対応済み」と書かない。

## 出力

実装のほかに、次を書き添える。

```markdown
### アクセシビリティで見た達成基準
- dialog: 2.1.2（フォーカスの閉じ込め）、2.4.3（開閉時のフォーカス）、4.1.2
- button: 2.5.8、4.1.2

### 目視で確かめること
- [ ] 閉じたあとフォーカスが開いたボタンに戻る（2.4.3）
- [ ] フォーカスの枠が背景に対して見える（2.4.7）

### [独自] の線引きを上書きしたところ
- （あれば。何を・なぜ）
```
